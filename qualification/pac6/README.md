# PAC-6 Windows consumer qualification

PAC-6 checks whether the pinned NSC_BUILDER v0.99 `--joinfile` path recreates
the same bytes from both legacy split layouts. The fixtures are deterministic,
synthetic byte streams generated by `fixture.py`; they do not contain Nintendo
key material or production data. They are independent consumer inputs, not
artifacts produced by NSCB.

In v0.99, the parser declares `--joinfile` with `nargs="+"`. Its join branch
uses `-tfile` when present and reads the first member path from that list file.
The invocation passes `--joinfile ""` to select the join mode; `-tfile`
supplies the member list. The empty argument is deliberate and is not an input
path.

## Pinned inputs

The consumer source is fetched from
`julesontheroad/NSC_BUILDER` at commit
`92690c0137f520b6ee4d6c20b6f5abe8a3ce5738`, tree
`358d753fe6cca11d5de8a2c60f7c1f25dad88442`. The preparation job archives only
`py/ztools` from that commit and omits files named `keys_template.txt`,
`title.keys`, `prod.keys`, `dev.keys`, or `keys.txt`, along with files whose
extension is `.key` or `.keys`. The consumer source is not patched.

The qualification uses Windows x64 and CPython 3.12.10. The pinned source
requests the latest Python 3 release but does not name a minor version. The
chosen runtime has an official Windows x64 build and supports the locked wheel
set. `requirements-win-cp312.lock` pins every direct and transitive package
version and wheel SHA-256. The preparation job records the Python and pip
versions, package filenames, versions, sizes, hashes, source archive hash, and
bundle manifest.

## Isolation and execution

The workflow runs only for PR #93, from its named branch to `main`, on a
`synchronize` event that changes `qualification/pac6/trigger.txt`. Both jobs
set `permissions: {}`, which disables all `GITHUB_TOKEN` permissions. GitHub
still creates the automatic token in the secrets context, but no step maps it
into a shell environment and the consumer process receives an allowlisted
environment. The workflow does not reference user-configured repository
secrets. The preparation job fetches the exact public PR head over anonymous
HTTPS, checks for credential variables, and prepares the pinned source and
wheelhouse. The separate consumer job performs no checkout and receives only
that run's bundle. It installs dependencies offline with hash checking. Before
using any bundled script or wheel, it checks the task revision, pinned source
identity, bundle file list, and every file hash. Before importing or running
the consumer, it checks for Git metadata, removes credential variables from
the consumer environment, and confirms that a direct-IP connection works. It
then installs an outbound Windows Firewall block for the isolated Python
executable and enables failure auditing for the Windows Filtering Platform
Connection subcategory. The second Python probe must produce event 5157,
which records a blocked connection. Its process ID, executable, destination,
TCP port, and filter origin must match the probe and the PAC-6 firewall rule.
The executable comparison uses the full NT device path resolved from its file
handle, rather than the `python.exe` basename. The workflow restores the
previous audit setting after the check. Missing audit privileges, an
unavailable event log, or a mismatched event stops the run before the byte
matrix.

The firewall rule applies to the Python executable used by `--joinfile`. The
qualification invokes only that pinned command path; other NSC_BUILDER modes
are outside this workflow.

## Cases and evidence

The workflow tests one member, a small three-member set, ten members indexed
0–9, and a production boundary of `0xFFFF0000` bytes plus one byte. It runs
each case with `.xcN` and `.nsN` names, serially. Before generating the large
fixture, the runner must have room for the input, an equally sized output, and
a 1 GiB reserve. Generation, output hashing, and comparisons use bounded
memory; the large output is removed before the next layout runs.

For every execution, `run_matrix.py` records the tested task revision, pinned
consumer commit and tree, runtime and dependency hashes, ordered member names,
lengths and hashes, input length and SHA-256, exact command arguments and
working directory, exit status, output length and SHA-256, and the comparison
result. The workflow uploads the compact JSON report and isolation evidence;
it does not upload the large fixtures or reconstructed outputs. PAC-6 passes
only if all eight executions exit successfully and match both input length
and SHA-256. This external consumer check covers indexes 0–9. NSCB's internal
resolver coverage through index 99 is a separate contract.

The workflow's required trigger file is created only after the workflow,
dependency lock, fixture generator, and report handling receive independent
review. A run that cannot establish isolation, prepare the locked dependencies,
or complete the matrix leaves PAC-6 unverified.
