# Use plan-first in-process jobs

Every mutating NSCB operation is resolved into an immutable, self-contained Operation Plan before execution. The plan carries all decisions, relevant configuration, selected providers, prerequisites, inputs, outputs, and conflict policy needed to execute without any later user input or prompting. v1 conflict policies are `fail` (the noninteractive default), validated atomic `replace`, and independent-item `skip`; automatic keep-both/renaming is not a conflict policy. Execution revalidates plan preconditions immediately before mutation and fails with a typed stale-plan/precondition-changed result rather than silently rewriting the plan when reality differs. Missing deterministic output directories may be created during execution when the plan proves the destination safe.

User-requested work runs as an in-process Job that emits structured progress and results. Planning precedes Job creation; a Job exists only after planning succeeds. Interactive TUI flows resolve every decision first, present the final Operation Plan summary, and require one explicit confirmation before creating/starting a mutating Job. Missing key prerequisites may be resolved interactively during TUI planning by selecting/configuring a valid `prod.keys` source, but explicit CLI/embedded requests return the typed prerequisite error and execution never prompts. `nscb` with no arguments enters the TUI only when attached to an interactive terminal; non-TTY no-argument invocation prints concise usage/help and exits with the usage class rather than reading a request from stdin.

The serialized `--plan`/JSON representation is an inspection artifact with no compatibility or replay guarantee and is not accepted as executable input. Standalone queued work is process-local in v1: queued Operation Plans are not persisted across restart, while bounded terminal Job history is. Durable terminal Job states are Succeeded, CompletedWithIssues, Failed, Cancelled, and Interrupted; No changes required and Already up to date are successful operation/result outcomes rather than lifecycle states. Independent-item batches may terminalize as CompletedWithIssues when some items publish successfully and others fail; that is a non-success CLI outcome with complete per-item results. Standalone exposes `jobs list`, `jobs show`, `jobs retry`, and `jobs clear`; retrying creates a fresh Job and freshly resolved plan, while retry-failed-items for CompletedWithIssues includes only the prior failed items and leaves prior successful outputs untouched.

NSCB does not require a daemon; v1 interrupted work never resumes automatically or from partial execution state. Process loss terminalizes the prior run as Interrupted, and an explicit retry creates a new Job with a freshly resolved plan linked to the prior run. Running work keeps its resolved execution context even if configuration changes; cancellation is cooperative with managed-process termination as a fallback, and execution never prompts for missing decisions or output conflicts.
