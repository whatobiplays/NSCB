# Keep content transformations explicit, composable, and evidence-driven

NSCB models retained content changes as explicit typed transformations rather than legacy processing modes or implicit cleaning profiles. Conversion may compose only mechanically required stages such as decompression/recompression; title-rights removal, delta removal, RSV/keygeneration lowering, update-partition removal, linked-account patching, trimming, splitting, and similar changes remain independently requested and visible in the Operation Plan, with eligibility and postconditions validated before publication. Multi-content packaging accepts structurally compatible related or unrelated titles with deterministic ordering. FAT32 splitting uses the broadly interoperable directory/archive split-set representation as NSCB's canonical default, with `.xc0`/`.ns0` and other qualified legacy layouts exposed only as explicit compatibility representations. Restoration is based on independently provable exact reconstruction rather than producer identity, and rename/inspection semantics use authoritative content-derived data unless enrichment is explicitly selected. Platform-safe filename sanitization is deterministic and visible in the plan; collisions introduced by sanitization, case folding, reserved names, or filesystem normalization must be resolved by an explicit deterministic naming policy rather than discovery-order numbering or random suffixes.
