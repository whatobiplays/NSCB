# Recognize content structurally and resolve deterministic logical inputs

NSCB recognizes content families through validated byte structure. Recognition is a separately requested, bounded, read-only operation, independent of Container Probe, Inspection, and Verification. Filename extensions produce a separate observation and never establish identity or resolve conflicting evidence. Unknown and Ambiguous are distinct typed results, both failing closed with CLI exit 3. Operational, malformed, truncated, unsupported-profile, and resource-limit failures are sanitized typed errors. No keys, decryption, decompression, helper fallback, title identity, or authenticity claims are introduced.

Validated PFS0 alone establishes its container family, not NSP/NSZ/NSX identity. An independently validated NCZ member establishes the compressed package representation. A valid card profile establishes the card-image family: the root partition sits at its documented placement, the root uses only known partition names once each with update, normal, and secure present, and every root entry bounds a partition HFS0. A compressed card keeps the copied source page address only inside the capacity its RomSize code declares and no later than its declared valid-data end; independently validated nested NCZ establishes the compressed representation. Absence of NCZ proof does not establish an uncompressed variant. Standalone NCA recognition is conditional on a supported readable NCA3 structural profile; ordinary encrypted headers have no keyless positive identity. NSX has no unique keyless byte discriminator and remains unestablished. Ticket-like PFS0 member names are observations only, using present, not_observed, and not_applicable; they cannot establish ticket validity, NSX identity, or eligibility.

The public scalar package_structure_eligibility describes structural consideration by future whole-container package/card-image operations. Its only states are eligible, ineligible, and not_established. PFS0 framing alone maps to not_established. Positively established standalone NCA or NCZ maps to ineligible. Validated top-level PFS0 containing validated NCZ maps to eligible. A valid XCI card header with the required HFS0 hierarchy maps to eligible, as does a valid XCZ structure with independently validated NCZ. Unknown, insufficient, or conflicting evidence maps to not_established. Nested archives do not make their container ineligible. The scalar grants no execution authorization, operation readiness, prerequisites, keys, or Verification and introduces no per-operation capabilities. Compression-compatible framing proves neither genuine Nintendo content nor correct decompression.

All nested parsing shares cumulative budgets, checked arithmetic, immediate-parent bounds, and bounded allocations; a cumulative parser-work ceiling of 1,000,000 units over NCZ descriptors and Zstandard frames and blocks returns the stable limit_exceeded result when exhausted, and only parser work is capped by it while the byte ceilings stay unchanged. Every applicable member is examined before success; malformed or budget-exceeding later members cannot be hidden by an earlier positive claim. Exact evidence profiles, sources, and ceilings are documented in [Content recognition](../content-recognition.md). The existing Container Probe contract remains unchanged.

A qualified split layout resolves to one logical Content file. Selecting any recognized segment resolves the complete set, while directory discovery collapses its parts to one input. Missing, ambiguous, overlapping, or inconsistent segment sets fail with typed recognition errors rather than being processed as partial content. Duplicate logical file identities supplied through overlapping independent selections remain a planning error rather than silently running twice.

Explicit CLI commands accept one or more path arguments, including directories, and additionally accept a typed JSON input-list file for large automated batches; this is an input-selection artifact, not an executable Operation Plan or Plan snapshot. JSON input lists are a versioned, stable 1.x input contract: compatible releases may add optional fields, while unknown required semantics and unsupported schema versions are rejected rather than guessed. Relative entries inside an input-list file resolve relative to the list file's parent directory; direct CLI relative paths resolve against the process working directory. Plans capture the resolved paths. Explicit arguments retain caller order. Each directory expansion is sorted deterministically by normalized relative path and inserted at that argument's position, with recognized split sets collapsed before duplicate-identity checking. Directory recursion and symlink traversal follow the established explicit opt-in discovery rules.
