# Negotiate device capabilities without managing Switch-side software

NSCB treats compatible Switch-side responder software as a user-owned prerequisite rather than something NSCB installs, updates, bundles, or manages. Each connection derives a typed device capability set and planning rejects unsupported device operations before execution instead of assuming behavior from a product/version label. Installation and storage transfer are distinct operations. Dump/backup scope is broader than content containers: v1 preserves the supported responder's qualified backup/export capabilities through NSCB-owned typed operations, including non-content data such as save data when the responder/provider contract supports it.

If multiple compatible Switches are connected, NSCB never silently chooses one: interactive flows ask, while explicit CLI/embedded requests require a stable selector from discovery; a sole compatible device may be selected automatically by the interactive TUI. Device storage destination is resolved during planning, with no silent fallback between explicitly selected targets. Capacity is checked and revalidated when the responder can report it; uncertainty is surfaced when it cannot.

A lost connection terminalizes the active operation with a specific interruption result; host sources remain untouched, host temporary artifacts are cleaned when safe, and device-side state is reported as unknown unless the protocol can positively prove completion or rollback. Dump output is staged on the host and validated with applicable local postconditions before publication rather than trusting responder transfer success alone. Retrying creates a fresh planned attempt rather than resuming partial v1 state.
