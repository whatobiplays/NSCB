# Negotiate device capabilities without managing Switch-side software

NSCB treats compatible Switch-side responder software as a user-owned prerequisite rather than something NSCB installs, updates, bundles, or manages. Each connection derives a typed device capability set and planning rejects unsupported device operations before execution instead of assuming behavior from a product/version label. Release qualification exercises specific known responder versions, but runtime admission is capability/protocol based: a newer or otherwise unlisted responder version may be accepted when it proves the exact MTP/DBI semantics required for the requested operation. Version strings alone never grant support, and unknown responder capabilities are never passed through generically; only operations explicitly modeled and qualified by that NSCB release are available.

NSCB owns a device-transport boundary with target-specific qualified adapters so the public Engine/device contract remains platform-neutral. DBI MTP is the primary v1 responder transport; host implementations may use the best qualified OS mechanism per target rather than forcing one MTP stack everywhere. DBI's separate custom `DBI0` bulk-USB backend may be advertised as a v1 Installation transport only if it is qualified on all four v1 host targets; otherwise it remains experimental/internal or deferred rather than creating platform-specific public capability drift. When both transports are qualified and available for installation, planning selects MTP by default unless the caller explicitly selects `DBI0`; the selected transport is part of the immutable Operation Plan and provenance. NSCB never silently switches transports if availability changes before or during execution: execution fails stale/interrupted as appropriate and a fresh retry may choose another transport. v1 device communication is local USB only; responder FTP/HTTP/network transports are deferred beyond v1. NSCB never launches DBI remotely, self-elevates, or performs privileged USB/system setup; it detects missing responder/driver/permission prerequisites and reports actionable setup instructions.

Installation and storage transfer are distinct operations. Unmodified Content files require the default Full Verification profile in the current Job before device mutation begins; valid required keys are a prerequisite and prior Job verification history is never reused as an authorization cache. Intentionally modified Content that invalidates original signatures may instead use an explicit modification-qualified Installation or Storage transfer path. Qualification depends on the actual file and positively recognized, permitted transformation semantics, not on which tool produced the modifications. NSCB validates all other applicable integrity checks, reports signature mismatch and qualified modification status, and never represents the result as Full Verification success; unknown/unqualified modifications are rejected. In an explicitly requested transform-then-device composite Job, the reviewed Operation Plan identifies this path and its confirmation authorizes it without a second prompt. Install-only or transfer-only standalone CLI requests require an explicit modified-content option; neither path may silently downgrade Full Verification. Installation must consume exactly the verified or modification-qualified bytes from an operation-owned stable snapshot or equivalently strong source guarantee; if source stability cannot be guaranteed, execution fails before transfer. v1 also supports explicit composite Jobs that perform one or more local Content transformations followed by Installation or Storage transfer in the same Operation Plan; every local and device stage remains explicit and independently validated. If a dependent device stage fails after a host transformation was successfully published, the overall Job is Failed while structured stage results retain the successful host artifact. Installation success requires the qualified responder/transport completion signal plus every available qualified postcondition, such as refreshed device-inventory confirmation where the protocol exposes it; NSCB does not claim byte-for-byte installed-state verification unless the responder can actually provide evidence for that claim. If exact requested title/version content can be proven already installed, Installation may return Already up to date rather than reinstalling; otherwise NSCB follows the responder's qualified deterministic install semantics instead of inventing a generic overwrite abstraction.

Storage transfer applies the same explicit `fail` / validated `replace` / `skip` conflict-policy model used for host output when the responder exposes enough destination identity/control to implement it safely; unsupported policies are rejected during planning rather than silently delegated to responder defaults.

v1 Dump models installed-title dumps, gamecard dumps, save backups, and Album-media export; arbitrary SD/NAND filesystem browsing or copying is outside NSCB. Installed-title Dump defaults to separate logical base/update/DLC Content files, with an explicit option for deterministic combined multi-content packaging. Gamecard Dump defaults to the full XCI; trimming is an explicit transformation that may follow in the same composite Job, while certificate export remains separately explicit. Save Dump exposes every qualified responder save category as typed scope and requires the requested title/user/category selection rather than silently dumping all save categories. Album Dump preserves original screenshot/video bytes and meaningful responder hierarchy beneath a deterministic Album output directory, subject only to platform-safe path sanitization. Save restoration and destructive device administration are deferred to the v2 roadmap. Dump/backup output may preserve personalized/private material by default when the modeled capability exports it, but NSCB must present clear warnings/notices that exported data can contain sensitive or private information. Gamecard certificates are a specific exception: normal XCI dump excludes the personal certificate, with an explicit sensitive-artifact option for separate certificate export.

Content Dumps require an available valid key source and are published only after the full applicable local cryptographic/structural postcondition set can run and pass. Non-content Dumps such as saves or Album media use type-appropriate validation rather than content verification. Save backups preserve the responder-compatible representation and may include a nonsensitive NSCB manifest rather than inventing a private archive format. All available device identity/provenance reported by the qualified integration may be retained in history/provenance.

If multiple compatible Switches are connected, NSCB never silently chooses one: interactive flows ask, while explicit CLI/embedded requests require a stable selector from discovery; a sole compatible device may be selected automatically by the interactive TUI. A plan is bound to the selected device identity and fails revalidation rather than substituting another connected Switch. Device storage destination is resolved during planning, with no silent fallback between explicitly selected targets. Capacity is checked and revalidated when the responder can report it; uncertainty is surfaced when it cannot.

A lost connection terminalizes the active operation with a specific interruption result; host sources remain untouched, host temporary artifacts are cleaned when safe, and device-side state is reported as unknown unless the protocol can positively prove completion or rollback. Dump output is staged on the host and validated with operation-appropriate local postconditions before publication rather than trusting responder transfer success alone. Retrying creates a fresh planned attempt rather than resuming partial v1 state.
