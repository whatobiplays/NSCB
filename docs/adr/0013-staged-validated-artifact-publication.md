# Stage and validate artifacts before publication

Mutating NSCB operations never modify source files in place and never destroy an existing destination before a replacement is complete. Standalone NSCB uses a deterministic, user-visible default `output_dir` for both single-item and batch work when the caller does not specify another destination: `NSCB_output` under the current user's platform Documents directory. If that Documents location cannot be resolved or the output directory cannot be safely created/written, planning fails with an actionable output-directory error rather than silently falling back to home, the current working directory, temp storage, or the executable directory. Generated package files are placed inline at that root by default, while operations that inherently produce a logical directory—such as extraction, directory-style FAT32 split sets, or save backups—create deterministic subdirectories beneath it. `output_dir` is normal standalone configuration and may be overridden per request; embedded hosts provide their own destination policy and do not inherit the standalone default. Device Dumps use the same output directory policy. Published outputs are user data and are never automatically pruned by cache, history, diagnostics, or workspace cleanup.

Temporary/intermediate work uses platform-appropriate application cache/temp storage by default rather than the user-visible output directory, with an explicit/configured workspace override available for large-storage needs. At standalone startup NSCB may identify abandoned NSCB-owned workspaces from dead prior runs, reconcile associated work as Interrupted where applicable, and remove only artifacts it can prove are NSCB-owned and disposable; it never recursively cleans an arbitrary user-selected directory merely because that directory is configured as a workspace root.

Final artifacts are built on the destination filesystem where practical, validated against operation-specific postconditions, and only then atomically promoted or replaced; helper exit success alone is insufficient. Coupled multi-artifact outputs such as split sets are staged and validated as one publication unit and, where practical, promoted through an atomic parent-directory replacement rather than exposing completed parts incrementally. Independent batch items remain independently publishable. Explicitly requested transformations inside a composite transform-to-device Job still publish their normal validated host artifacts; a later dependent device-stage failure never rolls those artifacts back. Install-only Full Verification remains read-only and does not create another host copy.

Rename/Sanitize is source-local by default rather than publishing into `output_dir`. A same-filesystem rename uses an atomic filesystem move where available. An explicit cross-filesystem destination is executed as copy, byte-identity validation, atomic destination publication, then source deletion only after success; the Operation Plan exposes that it is a cross-filesystem move. If source deletion fails after destination publication, NSCB reports a typed Move incomplete failure, retains both the original and validated destination, identifies both paths, and never claims that the move fully succeeded. Recognized split Content is renamed as one logical set rather than segment-by-segment independently.

Planning rejects duplicate resolved batch inputs, revalidates input identity and destination/workspace safety immediately before mutation, and execution detects source changes before publication so changed inputs cannot silently produce an accepted output. Atomic publication itself is a short non-interruptible critical section: if cancellation arrives after promotion has begun, NSCB completes that promotion to a known filesystem state, preserves the successfully published item, and prevents subsequent work.

When an explicitly requested transformation has nothing to change, NSCB returns a typed No changes required outcome and does not create a replacement artifact unless the operation itself requires a copy/repack. When an existing destination can be positively proven identical to the intended artifact, NSCB returns Already up to date rather than rewriting it; otherwise normal conflict policy applies. Generated artifacts receive ordinary safe destination-platform permissions and filesystem timestamps, without copying unrelated source metadata such as extended attributes, alternate streams, quarantine state, or timestamps unless an operation's data model explicitly requires it.
