# Use stable extracted-content manifests for repacking workflows

Extraction emits a versioned extracted-content manifest by default, describing the logical source structure, content roles/identities, and relative extracted paths; selective extraction records that the manifest is incomplete. Manifest payload paths are normalized relative paths confined beneath the declared content root: absolute paths, traversal outside that tree, symlink/hard-link indirection, and special filesystem objects are rejected. v1 manifest payloads consume regular files/directories only.

The manifest is a stable interchange format intended to cross process and time boundaries, so breaking changes require a new manifest version with explicit migration or rejection behavior. Unknown additive optional fields may be ignored or preserved where practical, while unsupported schema versions or unknown required semantic features are rejected. Users may intentionally edit extracted files before repacking: the manifest describes structure and intent rather than hash-locking payloads, while `pack` validates the current files and resulting structure; exact-original reconstruction remains the separate Restoration capability.
