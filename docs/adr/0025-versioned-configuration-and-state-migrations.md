# Version configuration and migrate durable state transactionally

NSCB versions its standalone TOML configuration and durable SQLite state independently. Standalone creates a fully commented `config.toml` on first launch so settings and their defaults are discoverable; if required application-state/config initialization cannot create that file, normal standalone startup fails clearly rather than silently operating with unpersistable defaults. Lightweight `--help` and `--version` paths may operate without initializing application state. Typed `config path`, `config show`, `config set`, and `config reset` commands manage the same configuration while manual editing remains supported. Secret values such as a translation API key may be stored directly in v1 TOML by user choice but are always redacted from config display, TUI summaries, machine output, history, and diagnostics. `config reset` resets configuration only and does not remove user key material.

Compatible older configuration is migrated in memory, while rewriting a hand-edited TOML file for schema migration is an explicit save/migration action with backup rather than an automatic launch-time rewrite; unsupported future/incompatible configuration fails clearly. SQLite Job/history state uses automatic versioned transactional migrations, preserves prior state on migration failure, and takes a recovery copy before migrations that cannot be trivially rolled back rather than silently recreating or discarding history. Standalone exposes `jobs list`, `jobs show`, `jobs retry`, `jobs clear`, and retry-failed-items behavior for CompletedWithIssues. Clearing Job history removes durable Job/result/provenance records and their retained diagnostic references, but never published outputs, provider caches, catalog/translation caches, configuration, or key files.
