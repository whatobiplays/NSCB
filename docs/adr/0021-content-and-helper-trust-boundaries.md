# Harden untrusted-content and helper trust boundaries

NSCB treats content files and helper outputs as untrusted inputs. Extraction is confined to its resolved destination root, rejects traversal and special-object materialization, and creates only regular files/directories in v1; parsers use checked arithmetic, container-derived bounds, and explicit sanity ceilings rather than trusting declared sizes. Inspection requires an available valid key source rather than degrading into a partial no-key mode. v1 exposes two typed verification profiles: Full, the default strongest applicable structural/integrity/hash/signature/cryptographic verification; and Structural, an explicitly requested container/layout/relationship validation that does not claim cryptographic authenticity. For the selected profile, every applicable check must actually run and pass for verification to succeed; a missing key generation or other required prerequisite is a typed prerequisite failure rather than partial verification success, while non-applicable checks remain distinguishable from failures. Structured results expose stable typed checks with applicability, pass/fail state, and sanitized context rather than provider-native text. Required key availability is resolved during planning/preflight whenever derivable from the input.

Standalone NSCB's default persistent key location is an NSCB-owned `prod.keys` copy in its application-data directory rather than a legacy-project-specific import path. v1 does not provide a special legacy NSC_Builder key-import command; callers may still provide/configure another key source explicitly. The exact first-acquisition/copy behavior for the managed default is defined separately from this storage decision. When a qualified helper needs keys, NSCB may pass the configured `prod.keys` path rather than copying key material into command arguments; raw key values remain excluded from logs, events, history, diagnostics, and machine output.

Helpers run by exact qualified path with a controlled working directory, typed argument vector, and sanitized environment; local transformation contracts do not rely on network access. NSCB never invokes a shell merely to launch a helper and never self-elevates through `sudo`, UAC, or equivalent—OS/device setup requiring elevated privileges is an explicit prerequisite outside normal Jobs. Restoration claims require exact validated reconstruction, content-changing patches are always explicit in the Operation Plan, and outputs that fail NSCB postcondition validation are never published as successful artifacts.
