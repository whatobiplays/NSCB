# Harden untrusted-content and helper trust boundaries

NSCB treats content files and helper outputs as untrusted inputs. Extraction is confined to its resolved destination root, rejects traversal and special-object materialization, and creates only regular files/directories in v1. Extraction selectors are typed against NSCB's normalized Inspection model and may select logical content role/title, container partition, NCA identity/type, or embedded relative path where meaningful; provider-specific selector syntax is never public API. An explicitly requested selector matching nothing fails with a typed selection error, and selected objects resolving to a duplicate normalized destination path fail instead of being renamed or overwritten. Parsers use checked arithmetic, container-derived bounds, and explicit sanity ceilings rather than trusting declared sizes. Inspection requires an available valid key source rather than degrading into a partial no-key mode. v1 exposes two typed verification profiles: Full, the default strongest applicable structural/integrity/hash/signature/cryptographic verification; and Structural, an explicitly requested container/layout/relationship validation that does not claim cryptographic authenticity. For the selected profile, every applicable check must actually run and pass for verification to succeed; a missing key generation or other required prerequisite is a typed prerequisite failure rather than partial verification success, while non-applicable checks remain distinguishable from failures. Structured results expose stable typed checks with applicability, pass/fail state, and sanitized context rather than provider-native text. Original-signature mismatches caused by intentional Content modification never become successful Full Verification. The separately and explicitly requested modification-qualified Installation path may validate recognized, permitted modifications and all remaining applicable integrity checks without claiming original-signature authenticity; unknown modifications fail qualification. Required key availability is resolved during planning/preflight whenever derivable from the input.

Standalone key resolution remains explicit CLI path, configured path, then the conventional `~/.switch/prod.keys`; NSCB does not automatically copy that file into application data and v1 has no special legacy NSC_Builder import workflow. A `keys set`/`keys update` action may validate and atomically replace the conventional standalone key file when the user explicitly asks; NSCB never silently refreshes it from another source merely because another file is newer. Files NSCB creates or replaces for key storage use restrictive user-only permissions where the platform supports them, and failure to create the key file without materially unsafe exposure is an error. `config reset` never deletes the user's key file; key removal is a separate explicit action. When a qualified helper needs keys, NSCB may pass the configured `prod.keys` path rather than copying key material into command arguments; raw key values remain excluded from logs, events, history, diagnostics, and machine output.

Helpers run by exact qualified path with a controlled working directory, typed argument vector, and sanitized environment; local transformation contracts do not rely on network access. NSCB never invokes a shell merely to launch a helper and never self-elevates through `sudo`, UAC, or equivalent—OS/device setup requiring elevated privileges is an explicit prerequisite outside normal Jobs. Restoration claims require exact validated reconstruction, content-changing patches are always explicit in the Operation Plan, and outputs that fail NSCB postcondition validation are never published as successful artifacts.
