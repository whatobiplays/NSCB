# Harden untrusted-content and helper trust boundaries

NSCB treats content files and helper outputs as untrusted inputs. Extraction is confined to its resolved destination root, rejects traversal and special-object materialization, and creates only regular files/directories in v1; parsers use checked arithmetic, container-derived bounds, and explicit sanity ceilings rather than trusting declared sizes. Inspection requires an available valid key source rather than degrading into a partial no-key mode. Verification uses a small typed set of verification profiles; the default is the strongest complete profile applicable to the content. For the selected profile, every applicable check must actually run and pass for verification to succeed; a missing key generation or other required prerequisite is a typed prerequisite failure rather than partial verification success, while non-applicable checks remain distinguishable from failures. Structured results expose stable typed checks with applicability, pass/fail state, and sanitized context rather than provider-native text. Required key availability is resolved during planning/preflight whenever derivable from the input.

When a qualified helper needs keys, NSCB may pass the configured `prod.keys` path rather than copying key material into command arguments; raw key values remain excluded from logs, events, history, and diagnostics. Helpers run by exact qualified path with a controlled working directory, typed argument vector, and sanitized environment; local transformation contracts do not rely on network access. NSCB never invokes a shell merely to launch a helper and never self-elevates through `sudo`, UAC, or equivalent—OS/device setup requiring elevated privileges is an explicit prerequisite outside normal Jobs. Restoration claims require exact validated reconstruction, content-changing patches are always explicit in the Operation Plan, and outputs that fail NSCB postcondition validation are never published as successful artifacts.
