# Copy-through publication qualification

The Issue #9 tests use temporary directories and generated bytes. They require
no keys, providers, proprietary content, network access, or devices. Copy-through
v1 tests are enabled only on macOS; other targets verify that planning fails
closed with `UnsupportedCapability`.

## Focused operation tests

Run the deterministic implementation and public API tests with the pinned
toolchain:

```sh
rustup run 1.98.1 cargo test --locked --lib operation::tests
rustup run 1.98.1 cargo test --locked --test operations
```

The internal tests exercise:

1. Bounded source copying, source evidence hashing, and byte comparisons. A
   truncation fails as `SourceChanged`; growth reads at most one byte beyond
   the planned length and stages no extra data.
2. Capacity arithmetic for source staging, an optional Replace recovery copy,
   and a fixed safety reserve, including insufficient-space boundaries and
   integer overflow. A retargeted-workspace-path regression proves the query
   uses `fstatfs` through the already-open workspace or creation-parent
   descriptor rather than resolving the pathname again. Host-default planning
   selects destination-local fallback for a cross-filesystem workspace when
   the destination volume is qualified; an explicit cross-filesystem workspace
   override returns `UnsupportedCapability`. The plan records strategy and
   parent identity and execution revalidates both.
3. Independent staged length, digest, identity, and byte checks when a
   producer reports success with corrupt output.
4. Cooperative source locking with a separately opened descriptor attempting
   `try_lock_exclusive` while publication and artifact-inventory finalization
   are independently paused. It must receive `WouldBlock` before execution
   returns and acquire the lock after return, deterministically proving that
   the shared source lock spans publication and result finalization.
5. A source mutation before promotion returning `SourceChanged`, plus a
   mutation in the final check-to-publish interval. When a mutation is
   detected after promotion, the result is `PublicationUncertain`; the
   published output and relevant artifacts are retained.
6. Destination no-clobber competition, proving an entry inserted before
   publication is preserved and classified with a typed destination result.
7. Replace races that inject a competing destination after the final baseline
   validation. The name exchange may leave planned bytes at the destination;
   the competing entry is retained and inventoried as displaced, and the
   operation returns `DestinationChanged`. A combined source and destination
   race verifies that post-promotion source mutation returns
   `PublicationUncertain` while both entries remain inventoried. Another test
   mutates the held displaced inode after publication's final comparison but
   before inventory; refreshed same-length content evidence changes a
   successful result to `DestinationChanged`. Missing or unreadable displaced
   evidence is classified as `PublicationUncertain`. The tests do not claim
   that the exchange is identity-conditional or that rollback is safe.
8. Source and destination baseline changes, parent retargeting, a persistent
   lock-marker retarget followed by an independent session, staging-operand
   replacement after final validation, already-identical destination checks,
   cancellation at destination-lock acquisition, independent session
   coordination, and shared-session admission. Snapshot tests cover execution
   progress, success, failure, cancellation, and `AlreadyUpToDate` as a
   successful outcome with Succeeded job status. The stale-admission-guard
   regression verifies a finished admission cannot clear a newer operation
   admitted through a clone of the same session. Independent sessions have
   separate admission state while executions in the same destination parent
   still coordinate through the marker; the tests cover both the same output
   and distinct outputs in that parent.
9. Artifact retention and reconciliation evidence after cleanup-path
   substitution, destination-parent movement, replacement, and uncertain
   publication. Cancellation after staging preserves a Cancelled outcome while
   exposing the validated stage bytes when safe removal cannot be proven. Tests
   verify role, identity, separately recorded and refreshed content digests,
   planned path, current path evidence, and retained state where available. Late-competitor checkpoints also replace the destination
   immediately before and after the pathname-based hard link. A pre-link
   identity/content mismatch returns `PublicationUncertain` and is not marked
   retained or counted; an exact post-link alias remains available after a
   later destination replacement.

   Final inventory opens a fresh directory-relative destination name after
   content hashing. If the name now identifies another entry or has vanished,
   the result is `PublicationUncertain`; the stale handle is not used to claim
   current path presence or competitor retention, and retained staging bytes
   remain counted. If a Fail-policy `linkat` reports `EEXIST` but the
   competitor disappears before its first capture open, the result includes a
   path-only unretained `UncertainEntry`, is `PublicationUncertain`, and counts
   no undocumented competitor bytes.

The public API tests exercise serialized plan `kind` and `nscb_version`, a
host-supplied non-persistent default workspace with an explicit per-request
override, authoritative destination baseline, source preservation,
`AlreadyUpToDate`, default Fail, explicit Replace, qualified one-part Split
rejection through existing input-resolution behavior, unsupported numeric Split
layouts, ordinary standalone files, workspace creation rules, and stale-plan
rejection. Shared `OperationSession` clones expose the same ephemeral
current-operation snapshot; separate sessions have independent state. Copy and
Replace expose the retained artifact inventory and a
`CleanupIncomplete` warning. Retained storage reporting excludes bytes shared
with the published output and includes separate recovery or displaced data.

### Final inventory and cancellation phase regressions

Deterministic Fail and Replace tests replace the published destination after
publication evidence has been recorded but before final inventory. They
verify that the planned output's identity and digest come from a retained
staging or recovery alias, while the competitor is represented separately
with its own current identity, length, digest, and retained-byte contribution.
Both operations return `PublicationUncertain` and preserve the competing
bytes. Fail also covers a competitor first observed when atomic no-clobber
`linkat` reports that the destination name exists, and Replace covers a
baseline change immediately before promotion. Both results inventory the
actual entry with bounded identity and content evidence. A deterministic
mid-capture mutation proves that unverified evidence leaves the entry
inventoried but unretained and excluded from the retained-byte total.

Final full-file checks run while `current_operation` remains `Executing`, and
cancellation is accepted through the last of those checks. Entering
`Promoting` is the cancellation cutoff; that phase begins before the final
workspace, staging-entry, and lock-marker operand checks. Those checks and the
following syscall are separate operations, so `Promoting` does not make the
syscall identity-conditional. `Completing` follows a successful publication
syscall for postconditions and inventory. The execution wrapper enters
`Completing` before cleanup, competitor capture, inventory, or result assembly,
including wrapper finalization after an execution failure. A cancellation
accepted before that handoff is observed and produces `Cancelled`; cancellation
is refused once `Completing` has begun. The regression pauses before artifact
inventory and verifies that the snapshot reports `Completing` with
`CancellationRequested`, a second cancellation request is refused, and the
terminal result remains `Cancelled` while staged output and a current
destination competitor retain their identity, content, and path evidence. An
already-identical destination skips `Promoting`, enters `Completing` after its
final comparison, and returns `AlreadyUpToDate` with Succeeded job status.

The destination-lock acquisition regression cancels at that checkpoint and
proves that the final pre-staging cancellation check creates no workspace,
staging directory, staged file, destination entry, or operation-owned artifact.

The admission-guard regression covers a completed guard dropped after a newer
operation is admitted through a shared session. It does not claim to exercise
an active stale guard: normal completion deactivates the guard before the
completed guard can be dropped after another admission.

## Qualification boundary and limits

Copy-through v1 is qualified only for the tested local macOS environment and
filesystem operations that pass runtime checks. Replace requires the volume's
Darwin `VOL_CAP_INT_RENAME_SWAP` capability and a successful
`renameatx_np(RENAME_SWAP)`. Non-macOS platforms, network filesystems, and
unverified volume or mount configurations remain unqualified.

The Darwin exchange compares names, not the identities recorded during
planning. A displaced entry that is actually captured and independently
verified is retained with its current identity and content evidence and
returns `DestinationChanged`; if post-promotion state cannot be proven, the
result is `PublicationUncertain`, and the competitor is unretained and
uncounted. No automatic rollback is attempted. Advisory source and destination
locks coordinate only NSCB operations using the same protocol. Arbitrary
same-user processes can race the final validation and publication syscall.

The last source check and publication syscall are separate. A noncooperating
source writer can change the source in that interval; the operation cannot
promise continuous source stability or prevent stale output from becoming
visible before a post-promotion `PublicationUncertain` result. Repeated hashes
and metadata observations do not constitute an atomic source snapshot.

For a late destination competitor, the implementation reads the observed inode
through a descriptor and keeps that descriptor open while creating and
verifying a pathname-based alias. Holding the descriptor prevents the observed
inode from being reused during the pre-link interval. The pre-link race can
still make the alias absent or identify a different inode. Identity, length,
and digest revalidation detects that condition and returns
`PublicationUncertain`; the alias is unretained and uncounted, and the operation
makes no claim that the earlier observed inode survived at the destination
pathname. The deterministic
`late_competitor_replaced_before_link_is_uncertain_and_not_counted` and
`equal_content_pre_link_replacement_cannot_be_retained_as_observed_inode` tests
prove this fail-closed boundary without assuming probabilistic inode reuse.

Once a private alias is created and matches the observation made before
linking, a later destination-path replacement does not alter that alias. The
`late_competitor_link_alias_survives_replacement_after_link`,
`late_fail_competitor_anchor_survives_second_replacement`, and
`late_replace_competitor_anchor_survives_second_replacement` cases prove that
the retained identity and content remain inventoried and are counted once.
`retained_verified_competitor_alias_uses_uncertain_role_with_complete_identity_evidence`
records a retained `UncertainEntry` with complete evidence. The equal-content
pre-link replacement case records the opposite accounting state: the linked
replacement has complete self-evidence but `retained() == false`, and its bytes
do not contribute to `retained_storage_bytes()`. Callers must inspect both the
retained flag and evidence fields instead of assuming the role establishes
ownership, retention, or anonymity.
Recorded identity and content fields preserve historical evidence, while
refreshed current path and digest fields describe the state observed during
inventory. Missing or unverifiable current evidence never inherits a retained
claim from a historical observation.

This observed-only, fail-closed limit is part of the approved Issue #9 v1
contract. It does not promise preservation of bytes independently removed or
modified by a noncooperating same-user process, and it does not make
`RENAME_SWAP` identity-conditional. Darwin `fclonefileat` and `fcopyfile` were
evaluated but do not provide an atomic snapshot of previously hashed content
during concurrent in-place writes.

The implementation retains staging, recovery, displaced, and uncertain entries
because pathname removal cannot be conditioned atomically on the observed
identity. Under Fail, `linkat` makes the retained staged artifact and published
destination hard-link aliases to one inode. Editing or truncating either path
changes published bytes. Current cleanup does not automatically unlink
operation artifacts. Manual reconciliation must not mutate artifact contents;
removal requires verified ownership, parent identity, unchanged file identity,
and content evidence. The result reports known retained storage bytes beyond
published output and returns an unknown total when identity or size evidence is
incomplete. The preflight free-space estimate uses an opened directory
descriptor, does not reserve capacity, and can be overtaken when another
process consumes space before or during staging. Embedding hosts must show the
cost and artifact inventory and support manual reconciliation. Staged file
contents are synchronized, but containing directories are not, so crash
durability is not claimed.
